# rules/ · 规则与技能（冻结区）

## ① 职责 / 不负责什么

**职责**：把「剧本该怎么写」表达成**同时给模型、给业务、给校验器**的一份东西。
- 五类规则的**规则文档**（人读）+ **机器可读表达**（校验器读）
- **技能/提示词**（skill）：让模型照着规则产出剧本
- 示例剧本（正例）与反例集（每条规则至少一个不合格示例）

五类规则：**R-1 可用词表** · **R-2 槽位边界** · **R-3 流程边界** · **R-4 节奏边界** · **R-5 降级规则**（定义见 `docs/` 设计基础 §四.1）。

**不负责**：不实现校验算法（引擎在 `core/`，检查器在 `compiler/checks/`）、不产生音频。

## ② 输入 / 输出契约

- 输入：`core/` 的 schema（规则表达必须能被 core 的引擎解析）。
- 输出：`{规则文档, 机器可读规则集, skill 提示词, 正/反例剧本}`。
- 下游：`compiler/checks/` 读规则集执行校验；`packs/` 引用规则集版本。

## ③ 验收条件

1. 五类规则**每条**都有：陈述、正例、反例、判法（机器/人）；
2. 反例集是**可执行的**：把反例喂给校验器必须被拦下（与 `compiler/` 联动测试）；
3. skill 提示词产出的剧本，在示例业务上**一次通过校验**（不通过则改提示词，不是放松校验）；
4. 规则集有版本号，`packs/` 能声明依赖的规则集版本。

## ④ 本层数据收集

无运行时数据。但须记录：**每条规则被触发的次数**（由 `compiler/checks/` 回传），用于判断哪类规则最常被违反（反过来改提示词）。

## ⑤ 依赖边界

- 允许依赖：`core/`（schema）。
- 禁止：`rules/` 不得包含任何具体业务的话术（那是 `packs/`）；不得实现校验逻辑。

## ⑥ 变更纪律

改规则 = 改契约 → 必须同步：`compiler/checks/`（校验器）、`docs/`（设计基础 §四.1）、已有 `packs/` 的合规状态（可能由"合规"变"不合规"，须回归）。

## ⑦ 冻结状态

**[冻] 冻结区**（规则是契约）。业务侧要自定义规则 → 放在该业务的 `packs/<业务>/rules.ext.json`（扩展位），**不得改本层通用规则**。
