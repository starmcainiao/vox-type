## 7.1 剧本是什么形状（口径澄清，先解决一个常见误解）

设计基础 §2.4 说要"用 DFA/正则语言算法判定剧本" —— 那是**终局目标**。本项目**当前**的剧本形态是：

**剧本 = 一个线性 plan 数组**（`rules/skill.md` §输出格式 已冻结：JSON 数组，元素是播报单元）。
- 线性 = 没有状态机的状态/转移构造，没有循环原语（`core.protocol.PRIMITIVES` 是封闭白名单：`SAY / SLOT / SAY_LIVE / PAD / LISTEN / PRELOAD / END`）。
- 因此「追问」在结构上的表现只能是**同一个 key 连续出现多次**；「自环」按字面**无法表达**（`retry_ask → retry_ask` 不是合法 plan）。
- 「用户意图分支」不在 plan 里：plan 是**一轮**的播报序列，分支由上层编排（状态机/规则）决定下一轮发什么 plan。

**这个形态决定了四属性的可判定边界**（7.3 逐条给判据），也决定了「不可判的部分」必须显式声明为不可判（7.4），**不得**用语义启发式假装判过——那正是"人肉评审伪装成机器证明"。

## 7.2 剧本源格式（`packs/<业务>/script.json`）

```json
{
  "script_version": 1,
  "terminal_keys": ["closing_thank_you"],
  "live_whitelist": ["asr_low_confidence", "user_off_script"],
  "max_retry": 3,
  "units": [
    {"key": "greeting_welcome", "rate": "normal", "variant": 1},
    {"key": "step_confirm_amount", "rate": "slow", "slots": {"amount": "¥500"}},
    {"text": "不好意思，我没听清，您能再说一遍吗？", "action": "SAY_LIVE", "reason": "asr_low_confidence"},
    {"key": "closing_thank_you", "rate": "normal", "variant": 1}
  ]
}
```

字段规格：

| 字段 | 必填 | 说明 |
|---|---|---|
| `script_version` | 是 | 整数，本版只接受 `1` |
| `terminal_keys` | 是 | 非空字符串列表 = **终态话术 key**（收尾/转人工/结束）。线性 plan 无 END 单元时用它表达「出口」 |
| `live_whitelist` | 是 | 字符串列表（**可为空**）= 允许使用 `SAY_LIVE` 的场景白名单（R-5） |
| `max_retry` | 否 | 整数，缺省 `3`；**声明值 > 3 → 违规**（R-3「追问有上限（最多 3 次）」是硬规则，不许按业务放宽） |
| `units` | 是 | 非空列表；单元字段沿用 `core.protocol` 的 plan 单元（`action/key/text/rate/variant/slots`）**外加源格式专有字段 `reason`** |

**单元级附加规则**（源格式比核心协议更严，违反即 `ScriptError`，消息含单元序号与字段名）：
- 每个单元必须**恰好**是 `key` 或 `text` 之一（`core.protocol` 同规则，此处复述以自足）；
- `reason` **只允许出现在 `SAY_LIVE` 单元上**（`key` 单元带 `reason` → 报错：key 单元不应有降级理由）；
- 未知字段 → **报错**（源格式是"给人和模型看的可 Review 文本"，typo 必须响，不得静默丢弃——这条是源格式规矩，不涉及 `core.protocol` 的既有行为）。

（`reason` 为什么在源格式里而不在 `core.protocol.PlanUnit` 里：见 7.5。）

## 7.3 五项机器判据（四属性 + 降级留痕）

`check_properties(script, source, pack=None) -> CheckResult`，逐条跑，**先结构后引用**，判定顺序固定（C1 → C2 → C3 → C4 → C5），避免同一问题报两次。
`source` = `compiler.load_source(root)`（已审核话术库），`pack` = `assets.load_pack(pack_root)`（已预铸资产，**可为 `None`**）。

```python
@dataclass(frozen=True)
class Violation:
    code: str              # 判据码（下表各条给出）
    unit_index: int        # 单元序号，**1-based**（与运行时事件的 part 对齐）
    key: str | None        # 相关 key（无则 None）
    message: str           # 必须含：判据名 + 实际值 + 上限/期望值

@dataclass(frozen=True)
class CheckResult:
    violations: tuple[Violation, ...]   # 空 = 全过
    skipped: tuple[str, ...]            # 被跳过的判据码（如 pack=None → ("key_not_prebaked",)）
```

**`skipped` 的纪律**：跳过 ≠ 通过。调用方必须把这个字段往外传（未来的报告层据此标 `incomplete`）；实现**不得**在 `pack=None` 时假装 C3c 过了。

### C1 有出口（对 §2.4 第 1 条「无非法吸收态」的当前形态映射）
- **C1a**：`units` 最后一个单元必须是**终态** —— `action == "END"`，或它的 `key ∈ terminal_keys`。否则违规 `code="no_exit"`，消息含末单元序号与它的 key/text 摘要。
- **C1b**：首次出现终态单元之后**不得再有单元**（线性 plan 里终态之后永远执行不到）→ 每个这样的单元报 `code="orphan_branch"`。
  > **一条 plan 只走一条路径（2026-09-17 由 T09 的示例包暴露，写进规格）**：线性 plan 表达不了分支。所以
  > ①「追问耗尽 → 转人工」与「追问后继续成功路径」**不能共存于同一条 plan** —— 分支由**上层编排**决定下一轮发哪条 plan；
  > ② `terminal_keys` 是**集合**（不同轮可以有不同的出口：正常收尾 / 转人工 / 结束），但**任一条 plan 只能终止一次**，终止之后不得再有单元（C1b 就是这条的机器判据）。
  > 反例（T09 卡初版真踩过）：把 `handoff_human`（∈ terminal_keys）放在第 15 个单元、后面还接「创建工单 → 承诺上门 → 收尾」——机器报 3 条 `orphan_branch`，人读也不通（刚说"转人工"又继续走流程）。
  > **码归属裁定（2026-09-17，T06 验收时）**：C1b 与 C3a 检的是**同一批单元**（终态之后的单元）。实现把它们统一以 `orphan_branch` 报一次（由 C1b 触发，C3 不重复报），本表初版没给 C1b 单独发码——**裁定沿用实现的读法**：`orphan_branch` 同时承担 C1b 与 C3a 的语义，不新造码。
  > 为什么不是"必须有 END 单元"：`rules/examples/ok_intake.json` 用收尾话术 `closing_thank_you` 表达结束、没有 END 单元且已被验收为**合规正例**（T02）。所以出口由 `terminal_keys` 声明表达，END 只是一个可选的显式写法。

### C2 追问有上限（§2.4 第 4 条「有界」的可判定部分）
- **C2a**：连续同 key 跑长度（`run_length`）必须 `≤ max_retry`。超过 → `code="retry_unbounded"`，消息含 key、实际次数、上限。
- **C2b**：`max_retry > 3` → `code="max_retry_exceeds_rule"`（消息含声明值与 3）。
  > 线性 plan 无法表达"提问后用户没答 → 再问"的分支，所以「追问」在结构上就是**同一 key 连续重复**。这条能抓到「同一个 key 追问 4 次」；抓不到"换着 key 追问"（那需要语义，见 7.4）。

### C3 全 key 可达且都被预铸（§2.4 第 2 条）
- **C3a 可达（结构）**：`units` 里出现的每个 key 都必须位于**首个终态单元之前**；违者 `code="orphan_branch"`（消息含序号与 key）——终态之后的单元永远命中不到。
- **C3b 已审核**：出现的每个 key 必须 ∈ `source` 的话术库（`PackSource.phrases[].key`）→ 否则 `code="key_not_in_library"`（R-1 的机器面：**禁止自造文案**）。
- **C3c 已预铸**：出现的每个 key 必须 ∈ `pack` 的资产 key 集合（`pack.assets[].key`）→ 否则 `code="key_not_prebaked"`。C3c 需要资产包：`pack is None` 时**跳过**该条并把它记进 `CheckResult.skipped`（**不得**默认判过）。

### C4 不夹带未审核文本（§2.4 第 3 条）
- **C4a**：带 `text` 的单元，其 `action` 必须是 `SAY_LIVE`（显式或由结构推断）。**`action == "SAY"` 且带 `text`** → `code="unreviewed_text"`（这就是 R-5 说的「用 `action=SAY` 伪装自由文本为资产命中」）。
- **C4b**：带 `key` 的单元**不得**同时带 `text`（用 `code="key_text_conflict"`）。
- **C4c**：`reason` 不得出现在非 `SAY_LIVE` 单元上（`code="reason_on_keyed_unit"`；与 7.2 的源格式校验同源，此处作为检查项复述，供不经 `load_script` 直接喂字典的调用方）。
  > `PAD / LISTEN / PRELOAD / END` 这些原语当前**不带文本**；一旦将来要带，必须先改本文档，不得由实现自行放宽。

### C5 降级留痕（R-5）
- **C5a**：每个 `SAY_LIVE` 单元必须有**非空字符串** `reason` → 否则 `code="live_without_reason"`（消息含序号与该单元的 text 摘要）。
- **C5b**：`reason` 必须 ∈ `live_whitelist` → 否则 `code="reason_not_whitelisted"`（消息含实际 reason 与白名单）。
  > `live_whitelist` 为空列表 = **本业务不允许任何 SAY_LIVE** —— 此时任何 SAY_LIVE 都会被 C5b 拦下。这是有意的：白名单必须是显式声明，不许"没写就当允许"。

## 7.4 明确不可判的部分（显式声明，不许用启发式糊过去）

以下属 R-3/R-5 的语义面，**本轮不做机器判定，登记为人工审查项**（本节即登记处）：

1. 「某个 key 到底是不是一句'追问'」——需要语义理解（本项目铁律：`compiler`/`eval` 不做语义分析）；
2. 「换着 key 追问」的累计次数（C2 只数连续同 key 的跑长）；
3. 「用户沉默到底/意图反复落入同一分支」这类跨轮死锁——**plan 只有一轮**，跨轮状态在上层编排，不在剧本可判范围内；
4. 「终态之后是否真的转人工」——`terminal_keys` 只是声明，是否真转人工由上层保证。

**登记方式**：`check_properties` **只返回违规**（空列表 = 全过）；上述四条既不是违规、也不进返回值——它们的载体是本节与 T06 卡，由人工审查接手。**不得**把它们塞进违规列表假装判过，也**不得**为它们自造启发式（例如按标点猜"这是不是问句"）。

## 7.5 跨批待办 ① 的裁定：`reason` 的落点（不动内核）

**裁定：不改 `core.protocol`。** 理由三条：

1. **`reason` 是"作者意图"，不是"执行事实"**。它属于剧本源（7.2），由写剧本的人和模型声明；而运行时需要的是"实际发生了什么"——`runtime/` 已经在事件里写了**自产的** `reason`（`say_live_text` / `key_not_prebaked` / `fingerprint_mismatch` / `audio_file_missing` / `engine_mismatch`，见 T07 与 `docs/06 §6.2`）。两层各自完整，**合起来才有"声明 vs 实际"的对照**，这是审计最需要的形态。
2. **改内核代价与收益不成比例**：`core/` 是冻结区，加字段要升大版本 + 迁移期；而"`SAY_LIVE` 必须带 reason"这条规则**只在写剧本时**有意义——plan 是编排层在运行时生成的，它里面出现 `SAY_LIVE` 时该带什么 reason 由编排层按剧本决定，协议本身强制不了（协议不知道这轮为什么走了自由文本）。
3. **机器可判性并未丢失**：T02 当初记的"不可被机器判定"是**因为当时设想用 `core.parse_plan` 去读剧本**，而 `_validate_unit` 会静默丢弃未知字段。T06 的检查器直接读**源格式**（`script.json` 的原始字典），`reason` 是一等字段 → C5 能判。**结论：降级为人工判是可避免的，本轮让它变成机器可判。**

**回归检验**（三条，T06 验收的硬判据）：把 `rules/examples/` 的现成单元按 §7.2 包成源格式喂进检查器（话术库取 `keylist.json` 的 7 个 key、临时包覆盖同样 7 个 key）：

| 例子 | 期望 |
|---|---|
| `ok_intake.json`（T02 已验收的合规正例，不含 END、不含 SAY_LIVE） | **零违规** |
| `bad_r3_deadlock.json` | 含 `no_exit`（末单元是追问文本）＋ 3 条 `live_without_reason`（序号 2/3/4 是自由文本）；**不得**含 `retry_unbounded`（三句文本各不相同，不构成"同一个 key 连续跑"） |
| `bad_r5_silent_fallback.json` | 含 `unreviewed_text`（`action="SAY"` 带 text）＋ `no_exit`（末单元不是终态）；**不得**含 `live_without_reason`（那个单元的动作是 `SAY` 不是 `SAY_LIVE`，走 C4a 而不是 C5a） |

## 7.6 跨批待办 ② 的裁定：R-3 的检查口径

**裁定：R-3 按「有出口 / 追问有上限 / 无孤立枝」三条可判定判据落地**（C1a / C2a / C3a），不按"自环"字面判——线性 plan 没有循环构造，字面自环不可表达（T02 边界留档 ②）。R-3 的语义残留（7.4 第 1–3 条）登记为人工审查项。

## 7.7 本轮不改的内核

`core/protocol.py`（原语集合、PlanUnit 字段、解析校验强度）、`runtime/`（判定语义与事件字段）、`assets/`（包格式与指纹）、`rules/`（规则集与 skill 文本）**本轮零改动**。T06 只新增 `compiler/` 下的剧本装载与检查模块，并只读 `assets/` 与 `compiler/source.py`。
