# 01 · 问题与被砍掉的范围

## 问题

语音 Agent 的对话里，**固定部分占大头**（流程话术、字段提问、确认回读、错误提示），
但它们现在和不确定部分（自由问答、异常处理）走同一条最贵的路：
**每一句都要过 LLM + 每一句都要现场 TTS**。结果是：

- 延迟被 LLM 首 token 锁死（300–1000ms，级联链路里的大头）；
- 成本按 token 线性增长，固定话术反复付费；
- 固定内容不可审核、不可版本化——说了什么只能事后听录音。

## 我们做的那一个环节

```
用户语音 → [VAD/端点] → [ASR] → [路由/状态机]
                                   ├─ 确定 → plan JSON ─┐
                                   └─ 不确定 → 云端 LLM ─┤
                                                        ▼
                              资产注册表(key→音频+版本+TTL+变体池) → 渲染器 → 播放
                                                        │
                                     命中=零 LLM 零 TTS ─┘ 未命中=本地 TTS / 云端流式
```

**做**：plan 协议、资产注册表、渲染器（三种后端同接口）、双工行为控制器、
预铸流水线（批量合成 + 自动质检）、对拍 harness（指标采集）。

**明确不做**（写在这里是为了防止范围漂移）：

| 不做 | 原因 |
|---|---|
| 端到端语音模型（训练自己的 S2S） | 资源密集；且端到端普遍存在文本智力退化，与我们「保智力」路线冲突 |
| TTS/ASR 基座 | 用现成零件（本地小模型或云 API 均可替换） |
| 通用语音 Agent 平台 / SaaS / 多租户控制台 | 大厂与成熟开源框架的正面战场 |
| 开放域闲聊 | 那是云端大模型的慢路，不是资产层的职责 |
| 让用户按键选菜单（IVR 式输入） | 输入侧菜单化=死板；菜单只作为**降级恢复路径**（识别不清时兜底），≤2 层 + 永远留「说人话」出口 |

## 与现有开源的关系

我们**不是**又一个语音 Agent 框架（pipecat / livekit agents 已经很好），
而是可以**插在它们里面**的一层：框架负责管线与传输，我们负责「话术资产化 + 双工参数化」。
协议设计原则：不绑死任一框架，plan JSON 与资产表可用任意语言实现。
