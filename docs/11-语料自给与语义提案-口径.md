# 11 · 语料自给与语义提案口径（T12 / T15 前置规格）

> **本文件是 T12（语料自给+真话术入库+golden set）与 T15（语义提案器实测）两批卡的规格依据**，由策划补定。
> 它回答三个问题：**从哪拿语料、拿到的东西凭什么可信、语义检索放在链路哪一段才不越红线。**
> 上游：`docs/10 §10.2`（命中口径与那条红线）、`docs/06 §6.1.2`（源格式权威）、`packs/AGENTS.md`（包是数据不是代码）、`eval/AGENTS.md`（golden set 与统计纪律）。

---

## 11.1 为什么要「语料自给」

现状：`eval/corpus/demo_broadcast.json` 只有 12 句自造话术，`packs/repair/` 是 16 key 的虚构报修场景。
两者都不足以回答「**预铸在真实口语面前能命中多少**」——因为真实用户不会照着我们的 variant 念。

**本口径要立的一条纪律：验证语料来自公开渠道、可复现获取、许可可查，不等任何人提供。**
凡对外报的数字，语料必须能由 §11.3 的台账 + §11.4 的命令在任意机器上重下并校验出一致的 sha256。

## 11.2 三条裁定

**裁定 1（语义检索的落点）：语义检索只做「上游选 key」的提案，不改内核命中判定。**
`docs/10 §10.2` 裁定 1 已定死：本层的命中判定只允许 key 直查 + 归一化逐字相等，**禁止**模糊/语义/embedding 匹配（理由：不可复核、会静默播"差不多但不是这句"的话）。
同一节的表格给出了出路，本文件把它确立为方案：

> 原文：「若要提速，**必须把固定话术改由 key 驱动**——这是上游的改动，不是本层能解决的。」

因此语义检索的**正确位置在接缝之上**：编排层用 embedding 把用户的自由说法映射成 key 候选，**然后照旧按 key 说话**；本层的逐字比对一行不改。
提案器的产物落 `labs/`（实验区，不进任何层契约）；**提案 ≠ 命中**，提案结果不得直接驱动播放。

**裁定 2（原始语料不进仓）：第三方语料落 `~/corpus/`，仓内只放脚本、台账、派生话术。**
三条理由叠加：① 本仓是公开预备仓；② 体量（吴语基准单份 2.4 GB）；③ 许可——**语料的许可必须逐份核到证据，不能信平台标签**（见 §11.3）。

**裁定 3（方言任务的标注责任）：方言集只有音频+转写，没有"该命中哪个 key"，映射由我们标注并写明口径。**
方言集本身不回答"这句话该命中哪个 key"——那是我们的业务判断。若不做这层标注就直接算命中率，等于自造命中，与 `docs/10 §10.3` 的口径冲突。
标注方式与 golden set 同格式（§11.5），并必须在报告里写明标注者与标注时间。

## 11.3 许可台账：字段与 fail-closed 规则

台账落 `labs/corpus-harvest-<date>/corpus.lock.json`，**每份语料一条**，字段固定如下（不得增删，需扩展走 §11.8）：

| 字段 | 含义 | 取值要求 |
|---|---|---|
| `id` | 平台上的仓库 id | `namespace/name` 原样，不得简写 |
| `platform` | 来源平台 | `modelscope` / `hf-mirror` |
| `kind` | 资源类型 | `dataset`（本批只允许 dataset） |
| `license_spdx` | 许可标识 | 见下方「许可判定」 |
| `license_evidence_url` | **许可证据的可点 URL** | 必须指向**文件内容**（READM 等），不得用平台列表页 |
| `size_bytes` | 平台声明的字节数 | 与下载后实测必须相等 |
| `sha256` | 平台声明的哈希 | 与下载后实测必须相等 |
| `fetched_at` | 下载时间 | ISO-8601 带时区 |
| `local_path` | 落盘路径（仓外） | **`${CORPUS_ROOT}` 锚定**（如 `${CORPUS_ROOT}/<来源目录>`）；**机器绝对路径一律不入库**——台账随仓公开分发，绝对路径既泄漏本机盘位布局（发布树红线）、又对别的机器不成立（T36 修正，2026-09-23） |
| `notes` | 备注 | 许可陷阱、字段结构等 |

**许可判定规则（fail-closed）**：
1. 以**语料自带的 README front-matter 或正文**为证据，**不以平台列表页的 license 字段为准**——平台会给大多数数据集自动填 `Apache License 2.0`；
2. 若正文与平台标注冲突 → **以正文为准**，并降级为「不可用」；
3. 许可不明 / 仅标 `unknown` / 属商业语料商产品（数据堂 `DatatangBeijing`、海天瑞声 `speechoceanadmin` / `haitianruisheng` 等）→ **一律不得下载入库**；
4. 下载前先取 README 判许可，**判据不通过就不下载**（不是下载后再补台账）；
5. 实测记录（2026-09-18）：数据堂数据集平台标 `Apache License 2.0`，而 README 正文写「版权归数据堂所有，商用数据」——**平台标签不可信已有实物证据**。

## 11.4 下载通道（本机实测，2026-09-18）

**已实测可用**（`docs/11` 里写的命令都跑过，不是纸面推测）：

```bash
# ① 语料元信息（含真实 license 字段）
curl -sS 'https://modelscope.cn/api/v1/datasets/<ns>/<name>'
# → Data.License = "mit"、Data.Downloads、Data.ReadmeContent

# ② 文件树（参数名是 Root=，不是 Path=）——**返回体自带 Sha256 与 Size**
curl -sS 'https://modelscope.cn/api/v1/datasets/<ns>/<name>/repo/tree?Revision=master&Root=<dir>'
# → Data.Files[] = {Type, Path, Size, IsLFS, Sha256}

# ③ 按文件下载（LFS 重定向会被透明处理，实测 sha256 与 ② 声明逐字相符）
curl -sSL 'https://modelscope.cn/api/v1/datasets/<ns>/<name>/repo?Revision=master&FilePath=<path>'
```

**环境侧三个坑（本机实测，必读）**：

| 坑 | 实测证据 | 处理 |
|---|---|---|
| `huggingface.co` 直连不通 | `curl` 返回 `000`，exit 28（超时 12 s） | 一律 `export HF_ENDPOINT=https://hf-mirror.com`（实测 200） |
| **git 全局代理是坏的** | `http.proxy=http://127.0.0.1:7890`，代理未运行 → 任何 `git clone` / `git-lfs` 立刻失败，**且报错文本是 `Failed to connect to 127.0.0.1 port 7890`，极易被误读成"网络不通"** | **不改全局配置**；命令内 `git -c http.proxy= -c https.proxy=` 绕过；下载优先走上面的 HTTP API |
| pypi 吞吐极低 | 12 s 只拉到 363 KB / 46 MB | 尽量不 `pip install` 大包；模型走 oMLX 自带 `/admin/api/ms/download`、`/admin/api/hf/download` |

落盘位置：`~/corpus/<id>/`（该卷实测 487 GB 空闲；`/` 只剩 37 GB，不得往系统卷写语料）。

## 11.5 golden set 格式与两个不同用途的集合

golden set 分**两个来源不同、用途不同**的集合，**不得混算一个命中率**：

| 集合 | 来源 | 用途 | 落点 |
|---|---|---|---|
| **A. 对照集（corpus-derived）** | 从语料里抽的**真实用户话术** | 量「真实口语 vs 预铸 variant」的差距；预铸准入判据的输入 | `packs/<biz>/golden/corpus_derived.jsonl` |
| **B. 验收集（hand-labeled）** | 真人标注（含真人对话确认） | 业务上线门槛的验收判定 | `packs/<biz>/golden/acceptance.jsonl` |

两者共用同一行格式（JSONL，每行一个用例）：

```json
{"case_id": "c0001", "utterance": "这个月工资延迟了，周转不开。", "expect_key": "empathy_hardship",
 "expect_kind": "key", "source_id": "tongyi_dianjin/DianJin-CSC-Data", "turn_ref": "d0007/t3",
 "labeled_by": "corpus-strategy-label", "labeled_at": "2026-09-18"}
```

字段纪律：
- `expect_kind ∈ {key, unspecified}`；`unspecified` = 该说法**不应**命中任何预铸 key（走自由文本档），**必须存在**，否则命中率是虚高的；
- `labeled_by` 必须写明标注者（`corpus-strategy-label` = 用语料的策略标注自动派生；`human:<id>` = 真人）；
- **对照集允许 `labeled_by=corpus-strategy-label`**（半自动），但**验收集必须是 `human:*`**；
- 语料的策略标注是**话轮功能**（12 类）而非话术模板，同一策略下有多种不同话术 → `expect_key` 允许指向**key 家族**，粒度由 T12 卡定。

**覆盖度口径**（T15 出数）：
- 逐字基线命中率 = 归一化后逐字相等的用例数 / 全部用例数（现状基线，`docs/10 §10.3` 的四步归一化）；
- 语义 **top-1 准确率** = 提案首位命中 `expect_key` 的用例数 / 有 `expect_key` 的用例数；
- 语义 **top-k 覆盖率** = `expect_key` 落在前 k 个提案内的用例数 / 有 `expect_key` 的用例数；
- **三个数必须同时报**，且报样本量与置信区间（`eval/stats.py` 的 bootstrap 口径）；只报其中一个 = 美化。

## 11.6 从语料到话术板：必须遵守的格式硬约束

派生 `phrases.json` 时，以下约束来自**已验收的实现**，不是建议：

1. **每个 variant 必须是一句**——文本中出现 ≥2 个句末标点（`。！？!?`）即报错（`compiler/source.py:167-192`）。语料里一句带多个分句的长话术**必须拆成多个 key**；
2. **`phrases.json` 只认 `key` / `variants` / `rates` 三个字段**，多一个都报错（`compiler/source.py:45-49`）；
3. **槽位不写在 variant 里**（`docs/06 §6.2.5`、`runtime/executor.py:225-231`）：槽值一律**现场合成**，作为独立音频段接在固定话术**之后**。所以语料里的 `[公司名称]` / `[姓名]` / `[手机号码]` 占位符**不得**留在 variant 文本中；带占位符的话术要么改写成「槽值可自然接在后面」的句子（照 `packs/repair` 的 `confirm_summary` 写法），要么不入预铸；
4. **包是数据不是代码**：`phrases.json` / `script.json` / `pack.json` 里不得出现任何 Python 逻辑，包内禁止 import（`packs/AGENTS.md:38`）；
5. **源里不得出现 `slots` 字段**——槽位是运行时数据，在资产层黑名单里。

## 11.9 实测记录（2026-09-18 首轮，原始数据在 `labs/corpus-harvest/`）

### 11.9.1 §11.3 台账字段的追加：多文件语料用 `files[]`

首轮实测发现 §11.3 的标量 `size_bytes` / `sha256` 无法表达多文件语料（一个数据集常含数十个文件）。
按 §11.8 追加，不覆盖：

- `files[]`：每个文件一条 `{path, size_bytes, sha256, declared_sha256, is_lfs, verified_against_platform, local_file}`；
- 顶层 `size_bytes` = 各文件之和；顶层 `sha256` = **manifest 摘要**（对 `(path, size, sha256)` 排序记录求 sha256）；
- `verified_against_platform=false` 表示**平台未提供该文件的哈希**（HF 镜像只对 LFS 文件给 `lfs.oid`），
  此时只记录了实测值——**不得把这个格子当作"已交叉核对"**。

### 11.9.2 §11.3 许可规则的加固：必须扫 README **正文**，不能只扫 front-matter

首轮实测事故：`MagicDataTech/magicdata-dialect-wu-chinese-tts-lite` 的 front-matter 与平台 `cardData`
**都写 `apache-2.0`**，而 README **正文**表格写 `CC BY-NC-ND 4.0` 并注明 *for non-commercial use only*。
只扫 front-matter 的第一版审计让它**假通过**了。

因此 §11.3 规则 3 追加一条**硬拒绝**（无人工放行口）：README 正文命中禁商用/禁演绎声明
（`NonCommercial` / `Non-Commercial` / `BY-NC` / `NC-ND` / `非商业` / 禁止商用 …）一律拒绝，
**即使 front-matter 与平台标签都写的是宽松许可**。

同类发现：**同数据的同名镜像不等价**——`MagicHub/...northeastern` 无 front-matter 许可、
`MagicDataTech/...northeastern` 有 `apache-2.0`，两者许可以正文为准都是 NC-ND。

### 11.9.3 §11.5 golden set 的两字段区分（**首轮最重要的口径澄清**）

`docs/10 §10.2` 的「逐字（归一化后）比对」，比的是**助手打算说的那句话**与包内 variant，
**不是用户说的话**。用户话术与客服话术是两拨不同的句子，拿用户话术去逐字比客服 variant
是**范畴错误**，不是"命中率低"（实测两臂都是 0/2433，但成因完全不同）。

因此 §11.5 的一行格式追加 `assistant_reply_free` 字段（原来只有 `user_utterance`）：

| 实验 | 输入字段 | 回答的问题 |
|---|---|---|
| ① 逐字档（现状基线） | `assistant_reply_free` | LLM 生成的那句话，能不能逐字命中预铸 variant |
| ② 语义档（T15） | `user_utterance` | 用户的自由说法，能不能被检索映射到正确的 key |

### 11.9.4 首轮实测数字（**三条都是负面的，且改变对外表述**）

| 测量 | 数字 | 样本 |
|---|---|---|
| 逐字档命中率（输入=助手自由文本） | **0.00%** | n=2433 |
| 语义档 top-1（匹配预铸 variant 原文） | **11.8%** | n=2064 |
| 语义档 top-1（策略级 12 类，**去掉自拟 key 设计**的对照） | **12.7%**（随机 8.3%） | n=2433 |
| 语义档 top-3 覆盖率（最好的一档） | 29.5% | n=2064 |
| 真实语料中句式可复用的话轮占比 | **1.8%** | 25810 客服话轮 |
| 流程决定性话轮占比（问候/确认身份/告别） | **23.0%** | 25810 客服话轮 |
| 一通电话里一句都预铸不了的占比 | **75.7%** | 1855 通 |

**对 §11.2 裁定 1 的补充（不推翻，是收窄）**：语义检索**即使只做提案**也不足以承担
「让上游按 key 说话」——top-1 与门槛 98.7% 差 8 倍，且换成语料自带标签体系同样低（对照实验已排除
"key 设计不佳"这个解释）。**key 只能由业务流程产出，不能由用户话术反推。**
预铸的适用边界因此是「**流程决定的话轮**」（23%）而非「全部固定部分」。

**数字外推限制**：以上语料只覆盖催收/账户服务一个场景，**不得外推到其他业务**；
流程驱动型业务（报修登记、查询播报）的可预铸率应显著更高，需另找该业务的语料实测。
