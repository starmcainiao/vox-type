## 一、一句话结论

**同一条链路、同一台机器、同一批话术**：固定话术的"决定好说什么 → 首帧音频"，走链路级实时合成是 **P50 586.7 ms（`say`，TTS 段，n=36）**，走我方预铸包命中是 **P50 0.232 ms（n=20）** —— 快 **≈2530 倍**；而链路里那台 Breeze-TTS 是 **42.3 s/次**（一次实测成功），实弹两轮均撞 **120 s 超时**后落 `say` 兜底。

**同时测出一个与预铸无关、但更要紧的事实**：链路整轮实弹 **52–173 秒**，**瓶颈不在语音段**——brain 自报 `queueWaitMs` **98.8–192 秒**，工具调用本身只要 3–18 ms。也就是说：**把 TTS 段压到 0，整轮仍是几十秒**。

## 五、对拍（我方 vs 链路）

**同引擎（`say`）同话术**的干净对照：

| 路径 | 首帧音频 | 相对 |
|---|---|---|
| 链路级实时合成（安静环境） | 586.7 ms（P50, n=36；三次会话区间 539–773 ms） | 1× |
| **我方预铸命中** | **0.232 ms**（P50, n=20） | **快 ≈2530×**（按区间算 2300–3300×） |

**换 Breeze 引擎时**：42.3 s/次（一次成功）→ 预铸快 ≈**182000×**；实弹里 Breeze 直接超时（>120 s），链路被迫降级到 `say`。

**成本侧旁证**：链路一轮的 reply 音频 286 KB（约 9 s 语音）由**云端/本地模型逐轮生成**；我方同长度音频是**包内文件**（T08 实测命中路径 `tts_calls = 0`）。

## 六、三条要紧的信息（与预铸无关，但影响项目判断）

1. **语音段不是链路瓶颈**：编排队列 98.8–192 s 才是。预铸解决的是"固定部分的合成延迟"，**不会**把一个几十秒的链路变成秒级——链路的其余瓶颈要单独治理。
2. **Breeze 在本机不可用**（对生产形态重要）：`_do_tts` 每次新起子进程 → 7.1 GB 模型**每次重载**（一次实测 42.3 s），超过 worker 内 120 s 超时即整体降级 `say`。这与 kefu-agent 自己的挂账（`交付-收尾批3-语音预热与推理预算`：~300 s、每轮落 say）一致，只是本次实测数字更小（42.3 s）。
3. **本机链路当前"能跑但不健全"**：`KEFU_MOCK=1` 也仍回降级话术，且 `prefetch: degraded`——**不要**把这些整轮数字当成"链路健康水位"引用；要引用就引用**段级**那几个数（ASR 0.93 s / LLM TTFT 1.59 s / say TTS 0.54 s）。

## 七、局限（未验证 / 已知偏差）

- **样本量小**：n=1~36，分位数只作量级判断；Breeze 只成功测到 1 次，其余两次是超时。
- **负载敏感、会话间波动大**（见 §三 的三会话表）：同机同引擎 P50 差 3 倍以上，`say` 有 4–6 s 尖峰。所有数字必须带 n 与工况引用。
- **"用户说话"是合成音**：ASR 段乐观看待；真人语音、带噪、口音未测。
- **LLM 被我换成本地 4B**：仓库 `.env` 原本是云端 SenseNova，两者不可比；本节所有 LLM 数字只对"本地 oMLX 档"有效。
- **业务后端 8090 未起**：真档轮的回复是降级话术，没走完整报修流程（mock 档也没走通）；因此**整轮数字不能代表业务健康水位**。
- **未测**：打断/双工、并发多会话、长音频、TTS 缓存命中率、端到端 S2S 对照。
- **我方预铸数字的来源**：T08 验收报告（同机、真 `say`、n=20、可复现）；本文未重跑。

## 九、这次实测对项目的三点含义

1. **预铸的价值被量化了**：同引擎下 539 ms → 0.23 ms（≈2340×），且命中路径 `tts_calls = 0`（成本侧为 0）。这是这个项目第一次拿到**外部链路**的对照。
2. **但"预铸 = 秒级语音"是错的预期**：链路的编排队列与 LLM/上游才是大头（52–173 s 实测）。对外讲收益时必须**限定在"固定部分的合成延迟"**，否则会被整轮数字打脸。
3. **本地 Breeze 这条 TTS 档不可用于生产**（每轮重载 7.1 GB）：这说明"本地 TTS 常驻 + 预铸兜底"的装配才是可行形态——正好是本项目的落点。

> 原始样本：`labs/chain-bench/raw/llm_cloud_samples.jsonl`、`live_turn_cloud_samples.jsonl`。

### 10.1 LLM 段：本地 vs 云端（同一批问句）

| 档 | n | TTFT P50 | min | max | 冷启/首连 |
|---|---|---|---|---|---|
| 本地 oMLX `Qwen3.5-4B`（安静档） | 6 | 4193.6 ms | 4121.5 | 4382.3 | 38615 ms |
| 本地 oMLX（另一会话，机器空载） | 3 | 1588.9 ms | 1577.7 | 1592.6 | — |
| **云端 SenseNova 6.8-flash-lite** | 5 | **3300.8 ms** | **1802.4** | **12728.9** | 16160 ms |

→ 云端**中位数略好、尾部更差**（1.8–12.7 s，方差来自网络与该 provider 的负载/限流）；**首连成本远低于本地冷加载**（16 s vs 38.6 s）。**云端真正的收益不是单次更快，而是不再与 ASR/TTS 抢本机算力**（见 10.2 的队列塌陷）。

### 10.2 整轮：四档配置对照（同机、同 3 句话、同一会话串行）

| 配置 | n | 端到端 P50 | 最快一轮 | brain 自报 `queueWaitMs` | 备注 |
|---|---|---|---|---|---|
| 本地 LLM + TTS 原样（120 s 超时） | 2 | 172384.7 ms | 171.6 s | — | 两轮 TTS 均撞 120 s 超时 |
| 本地 LLM + TTS 超时 1 s（→`say`） | 3 | 57777.6 ms | 52.4 s | 98750–191963 ms | **队列主导** |
| 本地 LLM + brain `KEFU_MOCK=1` + TTS 1 s | 3 | 85840.6 ms | 61.1 s | 98750–191963 ms | mock 也没救 |
| **云端 LLM + TTS 超时 1 s（→`say`）** | 3 | **54650.0 ms** | **25.6 s** | **0–6200 ms** | **本方案** |

**关键变化**：`queueWaitMs` 从 **98.8–192 s 塌到 0–6.2 s** ⇒ 之前那个"编排队列"根本不是调度器设计问题，而是**本地 LLM 把机器占住**造成的（本地 4B 常驻 + whisper 常驻 + Breeze 反复重载 7.1 G，互相抢）。LLM 上云后本机只剩 whisper + `say`。

### 10.3 剩下的 25–72 秒花在哪（云端档归因）

| 项 | 实测 |
|---|---|
| 工具调用 | `kb_search` 309–311 ms / `seat_status` 320–625 ms / `seat_transfer` 404 ms（都很快，且多数**失败**——业务后端 8090 未起） |
| 编排队列 | 0–6.2 s |
| ASR | ~0.9 s |
| TTS（超时 1 s → `say`） | ~1.5 s |
| **其余** | **每轮多次云端 LLM 往返**（路由 L3/L4 + 回复生成；日志里 `enqueued → 下一事件` 的间隔 20–30 s，与云端 TTFT 1.8–12.7 s × 多次调用吻合） |

→ **要把轮次压到秒级，落点在"减少每轮 LLM 调用次数"或"固定话术不经过 LLM"**，而不是继续优化 TTS。

### 10.5 风险与边界（必须写明）

1. **文本出网、音频不出网**：ASR 仍在本机（whisper 常驻），送云端的是**转写文本**——这是 kefu-agent 的既有口径，与"数据不出本机"原则的边界要按此理解，别宣称"全离线"。
2. **限流**：该 provider 在本次会话其它任务里多次出现 `tpm/rpm limit`；一轮里多次 LLM 调用会**放大**这个风险。目前 brain 对限流的退避策略未验证（本轮未撞到）。
3. **离线性**：云端档断网即不可用（brain 返回上游错误）；本地 oMLX 档可离线但慢且占机器——**两档都要保留**，按场景切换。
4. **业务后端 8090 未起**：三档的回复都是降级话术，因此 10.2 的绝对值**不代表业务健康水位**，只用于**同条件横向比较**。
5. **云端 TTS 未接**：kefu 的 worker 只认 Breeze（`mlx_audio` CLI）与 `say`，没有云 TTS 通路；本机 HF 缓存里 Qwen3-TTS-0.6B/1.7B、VoxCPM2 都是**空壳目录（4 KB，未下载）**，要走"更小的本地 TTS"得先下权重。
6. **Breeze 会留孤儿进程（本次实测到，运维要防）**：壳层对 worker 超时放弃后，**worker 及其 `mlx_audio.tts.generate` 子进程仍在后台继续加载 7.1 GB 模型**（本次清掉 3 个，RSS 合计约 300 MB 且仍在涨 CPU）。也就是说 `KEFU_VOICE_TTS_TIMEOUT_S` 收紧只让**壳层**不再等，**不会**终止那台重载——要么把 worker 一并杀掉/重启，要么干脆停用 Breeze 档。清法：`pkill -9 -f mlx_audio.tts.generate`。
