# 21 · 开源语音栈坐标与前置包适配判断（2026-09-23）

> **本文回答一个问题**：这些开源语音项目里，前置包（预铸资产层）能插在哪、怎么插？
> **来源**：2026-09-23 三路联网核查（端到端/统一模型 · TTS 模型 · 框架与接缝），
> 全部走官方仓库 / HF 模型卡 / 论文 / 官方文档，**每条事实附出处**；查不到的集中列在 §六。
> **上游**：`docs/12`（前置包定位）、`docs/10 §10.1`（接缝在哪）、`docs/17`（业界坐标）。
> **口径纪律**：本文只记**核实到的事实**与**由此可推的判断**；转述里对不上的地方在 §五 直接改正。

---

## 一、一句话结论

**所有这些项目都在解决「慢路怎么算得更快更好」；没有一个在做「哪些轮根本不用算」。**

- 所以它们**不是对手，是宿主**——前置包要插进去，找的是**轮级接缝**，不是跟它们比合成质量；
- 按接缝强弱排序：**Pipecat（骨架现成）> qwen-audio-agent（隔一层）> Realtime-Venus / Audex（只有轮级旁路）> SGLang-Omni 与各 TTS 模型（不是插入点）**；
- **「端到端的前置包」这个提法要拆开**：把前置包做成端到端模型 = 放弃可审核性（**不建议**）；
  把前置包挂在端到端系统上做轮级旁路 = **正解**，而且 2026-09 的现状让这件事第一次有了代码级落点。

---

## 二、按「有没有轮级接缝」分类

| 类别 | 项目 | 轮级接缝 | 前置包落点 |
|---|---|---|---|
| **端到端全双工 / 统一音频-文本模型** | Realtime-Venus（Omni 9B / Audio 9B）、Audex-30B-A3B、VoiceChat 11B | **无 TTS 接缝**（音频由模型内生）；但有「压制」与「解码器」两个可用点 | **轮级旁路**：命中轮播包、未命中轮才交给模型 |
| **级联框架** | **Pipecat** | **有**：`TTSService.run_tts`（官方换引擎接缝），且已有 `CachingTTSService` 先例 | **节点替换**（最直接） |
| **语音 Agent 编排层** | qwen-audio-agent | 接缝在「整个 voice frontend」这一级；Gateway 明确**不改** STT/LLM/TTS 配置 | 挂到它的**本地 HF speech-to-speech 前端**那一层 |
| **服务后端** | SGLang-Omni | **无音频旁路**（`ref_audio` 是克隆输入，不是输出旁路） | **不是插入点**；是「未命中用哪个引擎」的选项池 + 延迟基线来源 |
| **TTS 模型** | dots.tts、MOSS-TTS-Local、Confucius4-TTS、VoxCPM2、Fish S2-pro | — | 同上：**只影响未命中的那部分**（`docs/12 §12.4` 的 77%） |
| **桌面工具** | qwen-audio-toolkits | **无对话轮次**（单次请求-响应的工作台） | **不适用**——问题是「旁路某一轮」，它没有轮 |

## 三、三类落点的代码级证据

### 3.1 Pipecat：**骨架已经存在**，只是它按文本哈希、我们按状态

- 换引擎的官方接缝是抽象方法 `TTSService.run_tts(text, context_id)`
  （`src/pipecat/services/tts_service.py:549`，基类 `:111`）——实现它就能换引擎，
  `src/pipecat/services/` 下有 73 个 provider 子目录全走同一基类。
- **已有先例**：`CachingTTSService`（`src/pipecat/evals/tts.py:99`）——docstring 原文即
  「命中就播缓存音频、未命中回落内层服务并缓存」，**与我们的语义几乎一一对应**。
- **三条硬约束**（源码级，照抄即避坑）：
  1. 必须 yield `TTSAudioRawFrame`，**不能**用裸 `OutputAudioRawFrame`：只有前者会置
     `_tts_audio_received` 并触发 `BotStartedSpeakingFrame`（`transports/base_output.py:848-885`），
     用错会让下游轮次追踪、barge-in 判定全部失真；
  2. `TTSAudioRawFrame` 的音频必须**已是输出采样率的 mono 16-bit PCM**（无重采样，不匹配即 regenerate）；
  3. **替换节点实例，不要另插一个 FrameProcessor**——`TTSService.process_frame` 已经做了文本聚合、
     context id、打断处理与保序，另插会绕过这一整套。
- **状态来源它也自带**：内建 Flows（`src/pipecat/flows/`，含 `register_action` 扩展点），
  但 Flows 的 `tts_say` 走的是「文本→TTS」，**音频直放仍需覆盖 `run_tts`**。
- **与我们的差异（两条，都是要补的工）**：它的 cache key 是**文本哈希**
  （`sha256(cache_key + text.lower())`）——要「按状态取」得改 key 生成；它**没有预热 API**——
  但按 `<cache_dir>/<hexdigest>.wav` 命名投放即为预热，而 hexdigest 由调用方控制。

### 3.2 Realtime-Venus：**「让它别说」有官方开关，「让它说我的音频」只有客户端空间**

- 定性：**不是级联链路**，是端到端单模型（MiniCPM-o 4.5 基座 + Qwen3-8B 骨干 +
  离散 S3 speech token + 流式 flow-matching 解码器）。**没有可替换的 TTS 后端。**
- 但接口面是三个项目里最完整的，且是 Python `Protocol` 公开的：
  `PlaybackPort`（可注入的播放 sink，`harness/bridge/host.py`）、`VenusOmniServingPort`、
  `DelegateBackend`、`AgentSkill` 等，README 有「How to extend it」逐行替换说明。
- **压制点（可证）**：`ModelStep.suppress_audio` 字段 + `AudioDisposition` 枚举
  （`NONE / QUEUED / SUPPRESSED`）+ `SessionCapabilities.delegate_audio_filtered`；
  host 里是**闩锁**语义（「keep the gate closed until a fresh turn」）。
  → 模型标记出的私有 span，其音频被丢弃、不进播放队列。
- **结论**：**「丢弃模型音频」有官方开关；「换成自己的音频」没有官方路径**
  （`PlaybackPort` 的契约类型是 `GeneratedAudio`，无任何文档描述喂任意音频文件）。

### 3.3 Audex：**token→波形的解码器有公开 API**，是「缓存 token 而非缓存音频」的旁路

- 定性：统一音频-文本 LLM（单 Transformer 解码器；音频入 → 投影进文本嵌入空间；
  文本 token 与量化音频 token 统一生成）。**不是全双工**（见 §五 的更正 2）。
- `audex_causal_speech_decoder` 是**独立可加载包**，有公开编程 API：

  ```python
  decoder = AutoModel.from_pretrained(..., trust_remote_code=True).cuda().eval()
  session = decoder.create_session(chunk_frames=75)
  for sample_rate, samples in session.push([[123], [456]]): ...
  ```

  入参就是**裸 codec token 帧**，不依赖模型状态。
- → 理论上可**预先把固定话术的 codec token 算好并缓存**，运行时直接 push 进解码器出声，
  完全跳过 LLM 生成。**这是「缓存 token」的旁路**（需自己搭，非官方功能）。
- **两面硬约束**：① 许可是 **NVIDIA OneWay Noncommercial**（非商用，见 §五 更正 3）；
  ② **发布版刻意移除了语音克隆**（论文：为负责任发布「remove speech prompting abilities」，
  保留固定音色 TTS）——**要克隆音色就不能用它**。

## 四、「端到端的前置包」：一个说法，两件不同的事

用户提问里的「端到端的前置包功能」，在架构上是两个方向相反的命题，必须拆开：

| 命题 | 含义 | 判断 |
|---|---|---|
| **A. 把前置包「做成」端到端模型** | 训一个模型，输入状态、直接出音频 | ❌ **不建议**。理由不是技术上的：本项目全部卖点是**内容是可 Review 的数据**（`docs/14` 准入、`docs/20` 合规自审、指纹门禁、TTL）。做成权重 = 当场丢掉 diff / 审批 / 回滚 / 灰度——`docs/12 §12.10` 已写明「别让 DB 成为话术的真相源」，同理**别让权重成为话术的真相源**。而且实测已证伪「从用户话术反推 key」这条路（逐字 0.00%、语义 top-1 11.8%） |
| **B. 把前置包「挂到」端到端系统上** | 在端到端模型外面包一层：命中轮播包、未命中轮才进模型 | ✅ **这是正解**，也是 `docs/12 §12.3` 一开始写的「端到端 S2S 模型里做整轮旁路」 |

**B 的关键进展（这是本次核查最有用的一条）**：2026-09 的现状让 B 第一次**有代码级落点**——
Realtime-Venus 的 `PlaybackPort`（可注入播放 sink）+ `suppress_audio`（压制模型音频）+ 闩锁语义，
凑齐了「**这一轮别让模型出声，我播自己的**」所需的全部接口。
缺口只剩一条：契约类型是 `GeneratedAudio`，**「喂进任意音频」需在客户端侧实现**（自己实现 `PlaybackPort`）。

## 五、对转述里几处事实的改正（都基于官方源）

1. **`pipetcat` 不存在**，正确名字是 **Pipecat**（`pipecat-ai/pipecat`，BSD 2-Clause，15.8k stars）。
2. **Audex 不是全双工**——它是「统一音频-文本」。**全双工的是 NVIDIA VoiceChat 11B**
   （`nvidia/NVIDIA-NemotronLabs-VoiceChat-11B`，OpenMDW-1.1，2026-08-03）：
   Smooth Turn Taking 延迟 **448 ms**、User Interruption **480 ms**、入 16 kHz / 出 22.05 kHz、
   自称「首个支持工具调用的开源全双工模型」（**每个工具可定义 on-hold 话术，工具触发即播**——
   这一条与我们的「前置包播固定话术」在语义上高度接近，值得单独看）。
   顺带：**它是本次核查里唯一给出延迟数字的项目**。
3. **Audex 是非商用许可**（NVIDIA OneWay Noncommercial License）→ 与本仓 Apache-2.0 公开分发**不兼容**，
   要用只能隔离在仓外、且不得进入任何分发物。
4. **`netease-youdao/Confucius4` 不是 TTS**：它是 Qwen3.5-27B 的多模态**数学推理** LLM
   （Apache-2.0）。**TTS 是另一个仓库 `netease-youdao/Confucius4-TTS`**
   （零样本克隆、无需参考文本；输出 22050 Hz 单声道；官方无参数量与延迟数字）。
5. **Realtime-Venus 有两套许可**：代码与权重 **Apache-2.0**，**论文 CC BY-NC-SA 4.0**——
   对外引用论文内容受非商用条款约束，引用代码/权重则不受。**别混用。**
6. **四个端到端/框架项目没有一个公布首包延迟**（Realtime-Venus 论文无延迟指标节；
   Audex 只有定性「fast streaming inference」；qwen-audio-agent 的延迟数字是**任务执行延迟**
   −26.73%/−30.91%，口径完全不同）。→ **若延迟是关键判据，这几个项目在这一点上全是空白。**
7. **MOSS-TTS-Local-Transformer-v1.5 的名称没错**，但口径要准：骨干 **Qwen3-4B**、
   总参 **≈4.55B（BF16）**；音频 tokenizer `MOSS-Audio-Tokenizer-v2` 是 **2B 组合参数、最多 32 层 RVQ**，
   而 **Local v1.5 固定只取 12 码本**。
8. **fish.audio 那篇博客本次取不到**（域名在本机网络不可达，镜像与 archive 亦不可达），
   其数字**未核实**，本文不转述。S2-pro 可溯源的官方数字只有：许可 **Fish Audio Research License
   （非商用；商用需单独授权）**、模型卡单卡 H200「RTF **0.195** / Time-to-first-audio **~100 ms**」，
   以及 SGLang-Omni 集成文档的另一套口径（RTF 0.34、63.3 tok/s）——**两套口径硬件与配置不同，别混用**。
9. **dots.tts 的 MLX 支持是社区端口**（官方 README 列在 Community projects），不是官方维护。

## 七、对选型的含义（与「回到前置包本质」的关系）

1. **不要把 TTS / 音色当主线**——本次核查从两边都指向同一结论：
   这些项目全在「慢路更快更好」这条赛道上，而且资源比我们多几个数量级。
   我们唯一的位置是**「哪些轮根本不用算」**。
2. **但 TTS 侧有一条对我们直接有用的线索**：社区 MLX 端口 `sb1992/dots-tts-mlx` 有
   **`--enroll` 预计算音色向量**（`.dtprofile` <2 MB、可跨 int4/int8/bf16 复用、
   官方措辞「reference encode is paid once」）——**这正好命中我们卡住的那个点**
   （`docs/13 §五#23`：带参考音频时 ~0.3× 实时，根因是每次合成都要做参考条件化）。
   → 若要走「实时 + 克隆音色」，这是目前证据最硬的候选路径。
3. **第一个该做的适配器是 Pipecat**（见 §3.1）：骨架现成、有活跃社区、且它自带 Flows 状态机
   （等于把「状态来源」也给了）。比现在的 kefu 钩子（自造宿主）更有对外说服力。
4. **Realtime-Venus 只能做接口级设计，不能实测**——本机无 CUDA、无 A100。
   任何关于它的结论都必须标注「纸面推断，未实测」。
