# 10 · 接入取景与「命中」口径（T11 前置规格）

> **本文件是 T11 卡的规格依据**，由策划补定。它回答一个问题：**把预铸包插进真链路（kefu-agent）时，"命中"到底以什么为判据、能指望多高的命中率。**
> 上游：`runtime/AGENTS.md §②`（对外只暴露"一个接缝 + 一个旁路开关"）、`docs/02 §2.1`（plan 是控制面）、`docs/09`（链路实测）。

---

## 10.1 接缝在哪：我们坐在"决定说什么"与"把话说出来"之间

```
用户音频 → [ASR] → 文本 → [brain/编排] → 「这一轮要说什么」 → [TTS] → 音频
                                              ↑
                                    本层插在这里（一个接缝）
```

本层**不碰** ASR、不碰语义判定、不负责"该说什么"。它只回答一件事：**给定"要说什么"的表示，能不能用预铸资产把它立刻变成声音。**

## 10.2 「要说什么」的两种表示，决定命中率天花板（**这是 T11 最重要的裁定**）

| | 上游给的是**自由文本** | 上游给的是**话术 key** |
|---|---|---|
| 典型来源 | LLM 逐轮生成回复（kefu 现状：`sensenova` 生成中文回复；**勘误 2026-09-19**：docs/15 勘察更正——kefu brain 流程轮逐字取 yaml 预设话术，仅闲聊/FAQ 走 LLM，故上表的「来源二」才是 kefu 固定句的真实来源） | 脚本/表单流程驱动（设计基础里的"剧本"假设）、固定提示（降级/转人工） |
| 本层怎么判命中 | 只能**逐字（归一化后）比对**包内 variant；**不许语义近似匹配**（那要模型，越界且不可复核） | 直接查 key × variant × rate |
| 命中率天花板 | **低**（LLM 每次措辞不同，逐字比对天然难命中） | **高**（流程固定则句子固定） |
| 结论 | 若要提速，**必须把固定话术改由 key 驱动**——这是上游的改动，不是本层能解决的 | 本层的设计假设就是这一档 |

**裁定**：
1. 本层的命中判定**只允许两种**：(a) key 直查；(b) **归一化后逐字相等**（归一化口径见 10.3）。**禁止**模糊/语义/embedding 匹配——理由：不可复核、会静默播"差不多但不是这句"的话（红线）。
2. **命中率的责任划分要写清**：本层负责"给了 key/原文就能零调用播放"；**上游是否按 key 说话**决定上限。对外报命中率时必须同时报"上游表示形态"（自由文本 / key），否则数字会误导。
3. T11 的演示要**两种形态各跑一遍**：脚本驱动档（显式 key 驱动，演示高命中）与 LLM 自由文本档（演示逐字比对的低命中 + 未命中按开关走原 TTS），并把两档数字并列。
4. **（2026-09-21 新增，T33）多句输入的「逐字覆盖」是 (b) 的允许扩展**：上游一段话里含多句
   （kefu 预设话术天然多分句）时，允许把输入按包内 variant 的**归一化文本**逐段覆盖——每段仍是
   **归一化后逐字相等**，输出是按输入顺序拼接的段序列；任一段覆盖不上即**整体未命中（不播部分）**。
   这不是近似匹配：不含编辑距离/语义/去标点，播出内容 = 输入的逐字符重建（每段音频都对应输入里
   真实存在的一段字）。口径、算法判据与边界见 §10.7。

## 10.3 归一化口径（"逐字相等"到底怎么比）

比对前对两侧文本做**确定性**归一化，只有这四步，**不得增加**：

1. 去除首尾与内部所有空白字符（含全角空格 U+3000）；
2. 全角↔半角统一（ASCII 可见区与常见全角标点，含 `，。？！：；（）` → `, . ? ! : ; ( )`）；
3. Unicode NFKC 归一（处理兼容字符）；
4. 大小写统一（小写）。

**任何"同义改写、去语气词、去标点后比较"都不许做**——那属于语义，做了就等于自造命中。归一化函数必须**单元可测**（同输入必得同输出，且对上述四步各有正反例）。

## 10.4 旁路开关与失败语义（照 `runtime/AGENTS.md` 与 red line）

| 情形 | 行为 |
|---|---|
| 命中（key 直查或逐字相等） | 用包内音频拼接播放，**零 TTS 调用**；事件 `hit` |
| 未命中，且 `allow_fallback=False`（默认） | **fail-closed**：抛错中止，**不播任何替代音频**（不得悄悄走原 TTS） |
| 未命中，且显式开启降级 | 走**注入的**慢路合成器（kefu 的 TTS 或 `say`），并出 `miss` 事件，`reason` 必须区分：`key_not_prebaked` / `text_not_prebaked` / `engine_mismatch` / `audio_file_missing` / `fingerprint_mismatch` |
| 引擎不一致（包音色 ≠ 当前引擎） | 一律 `fallback`/`engine_mismatch`，**不得播过期音色** |

**事件字段名**一律引 `core.metrics_spec`，本层**不得自造**字段名；若需追加（如 `match_mode`），只能**加**，不得改名。

## 10.5 T11 的产物边界（不碰 kefu-agent 的代码）

- 适配器放在**本仓**：`adapters/framework_kefu/`（`adapters/*` 是扩展区，加目录零内核改动）；
- 它通过 **kefu 已有的公开接口**工作（不修改 kefu 任何文件）：
  - ASR：`voice_worker.py` 的 stdio 行协议（`{"op":"stt","wavB64":…}`），或 8096 的 `/api/voice/turn`；
  - 「要说什么」：`POST 127.0.0.1:8092/chat/turn`（brain）；
  - 慢路合成器：kefu worker 的 `op=tts`（`say` 档）或本仓 `adapters/tts_macsay`。
- **要动 kefu 的代码（例如把 brain 的输出改成 key 驱动、或在它的 voice 服务里插旁路）→ 另开跨仓卡，先经用户批准**；T11 不做。

## 10.6 T11 要回答的数字

1. **命中档**：首帧音频延迟（本层 vs 慢路）、**TTS 调用次数（命中必须为 0）**、事件齐备；
2. **未命中档**：按开关分别验 fail-closed（抛错、不落盘、不播替代）与显式降级（有 `miss` 事件、原因可区分）；
3. **两档命中率**（脚本驱动 vs LLM 自由文本），并注明上游表示形态——这是 T13（预铸准入）的输入。

## 10.7 序列命中：「整段 → 多段拼接」的口径（T33 新增）

**背景**：预铸准入（`docs/14`）准的是**一句一 variant**（`docs/06 §6.1.4` 字模最小粒度 = 一句），
所以多分句整段（如 kefu `opening`）不在包内；上游说整段时整段查不到 → 走原路（秒级合成）。
本节的「序列命中」把这一档接进快路：**整段按段覆盖，每段仍是逐字相等**。

**定义**：给定输入文本 T 与包 P，若存在 P 内 variant 的归一化文本序列 `(v₁…vₖ)`（k ≥ 1），
使 `normalize(T) == v₁ + v₂ + … + vₖ`（逐字符拼接相等），则称 T 被 P **逐字覆盖**，
命中结果为这些 variant 对应的资产条目序列。k = 1 时退化为 §10.2 裁定 1 的 (b)。

**算法判据（冻结，实现不得另立）**：
1. 比较一律在**归一化空间**（§10.3 四步，两侧同口径）；
2. 从位置 0 起，每步取**能匹配当前位置的最长**归一化 variant 文本（最长优先）；
   同长度多候选时取文本索引里的**首条**（与 `pick_by_text` 的"顺序稳定"同源）；
3. 消费该段后从新位置继续，直到覆盖完毕（命中）或某位置无可匹配项（未命中）；
4. 每一步的候选都必须通过 `pack.lookup` 的指纹/存在性复核（§10.4 的 `fingerprint_mismatch` /
   `audio_file_missing` 语义不变——复核不过 = 该候选不可用，从候选中剔除）；**全部候选都不过 = 未命中**；
5. 命中与未命中都**不抛错**（结论靠返回值读，与 `find_hit` 同族）；未命中时须带
   **未覆盖剩余文本**（供留痕与诊断），供调用方决定 fail-closed 还是降级。

**为什么最长优先**：唯一候选与多候选都要有确定性答案，且要让"更长的完整句"优先于"它的前缀句"
（包内若同时有 `您好。` 与 `您好，我是供热智能客服小暖。`，整段应命中后者）。这是可复核规则，
不是"更聪明"——它不做任何相似度判断。

**不做什么（红线不变）**：
- 不做近似匹配（编辑距离/语义/去标点）——§10.2 裁定 1 不动；
- 不做**部分播放**：任一段覆盖不上即整条未命中（宁可走原路，不播半句）；
- **不做段序约束**、不做重排/去重：输出顺序 = 输入顺序、逐段对应——输入本身乱序时播出也按该顺序
  （仍是逐字对应，没有播输入里没有的话）。加段序约束会让「确认句 + 提示句」这类真实混搭输出
  无法命中，得不偿失；
- 允许**同文本段别名**：包内两条资产文本相同（数据事实，如 `clarify_work_order__2` 与
  `clarify_repair__3`）时按算法判据 2 取索引首条——播出音频与该文本的任一条等价（同文本同引擎），
  记账 key 可能与"预期归属"不同，这是允许的（不改变听感，也不改变逐字判据）；
- 不允许"跨段吞并"：每段必须对应包内一条 variant 的完整归一化文本（不许截断 variant）。

**与 `find_hit` 的关系**：`find_hit` 是"单段逐字"的既有契约（T29 公开 API，语义不变）；
序列命中是新入口（`find_hit_sequence`），**不改 `find_hit` 的行为**。

两者在**候选口径上是有意不同的**（2026-09-21 审计后明确写清，不是缺陷）：
- 序列档只认 **`part_index == 0` 且 `rate_key` 精确匹配**的条目（且必须过 `confirm` 的指纹/存在性复核）
  ——即"当前语速档的完整首片"；
- `find_hit` 的文本档沿用 T29 的既有回落（同一句只有别的 rate 档时可退到该档；文本索引不筛 `part_index`）。

因此存在两类**预期内的不一致**：某句只在非当前 rate 档有资产时，`find_hit` 命中而序列档未命中；
某句只以 `part_index > 0` 存在时同理。**序列档的收窄是 fail-closed 的一部分**（宁可不命中、
走原路合成，也不播非当前档位的音频）。为了让"本该命中却换了路径"事后可定位，
`SequenceHitResult` 带 **`blocked_by`** 诊断字段：文本能匹配、但被 rate/part 口径剔除的候选标识
（**只进诊断，永不进命中**——与 §10.2 裁定 1 的红线一致）。

钩子（kefu 侧，T30）当前只接单段档；接序列档要另一张跨仓卡（多段拼接与音色一致性在钩子内落地）。
