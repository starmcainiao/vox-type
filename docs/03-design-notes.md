# 03 · 设计结论（为什么这么设计）

本文件沉淀几轮设计讨论的核心结论，每条都对应一个具体的坑。

## 3.1 字模是「整句浇铸」的，不是从连续语音里切的

历史上被淘汰的拼接合成（unit selection，1990s）之所以一听就假，是因为它从连续录音里
**在句内下刀**——切点两侧频谱/基频/能量对不上。本方案的字模是 TTS **完整生成的整句话**，
头尾天然完整，**拼接只发生在句边界**，垫 120–300ms 停顿即还原自然说话节奏。

**这条是设计红线：字模最小粒度 = 一句（含完整语调轮廓）。**

## 3.2 唯一合法的词级拼接：封闭词表

数字、金额、日期、是/否——词表封闭、播报语域固定（无情感起伏），逐单元拼接不违和。
电话系统用了几十年（Asterisk `SayNumber/SayDigits/SayMoney` + 预录音频包即活化石）。
**开放域不得做词级拼接。**

## 3.3 真正的风险是一致性，不是拼接本身

| 风险点 | 对策 |
|---|---|
| 句内槽位拼接（「您说的是 X 吗」是全链路唯一句中拼接处） | 短槽直接拼 + 槽前后 50–150ms 微停顿；长槽整句现场合成，不拼 |
| 跨批次一致性 | 同一 TTS、同模型版本、同音色参数、统一响度（同 LUFS）；换音色**整库原子重铸**，禁止新旧混用 |
| 档位一致性 | 固定层钉一个播报语速/情感档，槽值现场合成用同档参数 |
| 复读机感 | 同一状态存 3–5 个变体轮换/随机 |
| 预铸质检 | 流水线自动检查：头尾静音长度、削波、响度归一、采样率统一——不等用户听出来 |

## 3.4 预存的是话术，用户数据不预存

资产库存的是**静态、可审核、可版本化的话术**；
用户信息（手机号、地址、问题描述）**一律现场合成、不落资产库**——
既是隐私设计，也让资产库保持可公开（本仓库可开源的根本原因）。

## 3.5 价值表述：把隐式权重记忆外化成显式资产记忆

端到端语音模型不查表，它逐 token 生成；高频话术是被「压」进权重里的——
隐式、有损、不可编辑、不可审核。本方案做的事，是把这部分**搬出来变成显式资产**：
可编辑、可审核、可版本化、零推理成本、零首包延迟。

因此本层与端到端模型**不冲突、不必二选一**：E2E 管「活」的部分（自由问答、异常处理），
资产库管「死」的部分（流程话术、确认回读）。E2E 迭代下沉时，本层抽象为
「应答资产层」继续成立（输出音频同样可以缓存）。

## 3.6 交互死板问题的边界

- 死板的从来不是「预存」，是「让用户适配系统」：输入侧被迫选择、话术零变体、接不住离题。
- **输出侧预铸 = 无感**（用户不知道哪句是预存的）；**输入侧菜单化 = 限定用途**（仅作降级恢复）。
- 菜单作为恢复路径的规则：≤2 层嵌套、永远留「说人话」出口、识别置信度低才启用。

## 3.7 空间换时间：交换率极度划算

一套表单流程 50 状态 × 3 变体 × 均长 8s ≈ 2.7 小时音频 ≈ Opus 约 30MB（WAV 约 310MB），
对比本地 TTS 模型本体 3GB+ 与云端每句 token 成本。
**真正的代价不是空间，是陈旧性**——TTL/事件失效/版本标签是必做件
（Vapi 公开案例里客服团队踩过「缓存了过期产品信息」的坑）。
