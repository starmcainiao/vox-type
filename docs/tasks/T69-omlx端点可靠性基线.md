# T69 · oMLX 端点可靠性基线（先取证，不先修）

> 状态：待开批
> 来源：T1「业务产品票」G1（使用者视角最痛的一条）+ 「开发交付票」的复现失败记录
> **本卡只写诊断与取证，冻结区一行不改。** 理由见 §二。

## 一、现象（原始报告）

「业务产品票」按 `docs/22-五分钟跑起来.md` 的 Quick Start 实跑，**4 次里 3 次失败**，
失败形态是某一句的音频**约 327 秒**，被 `compiler/quality.py` 的
`MAX_DURATION_MS = 30000` 判 rc=4 质检不通过。

**这是最对外的那条路径**——新用户第一次上手走的就是它。
2/4 的失败率不是「有个偶发 bug」，是「第一印象随机翻车」。

## 二、为什么本卡**不**预先指定修法

我在写这张卡之前**自己直接探过端点**（3 次通用句 + 3 次那条失败原文的 key 句），
全部正常：音频 1.4–8.0 秒，墙钟 1.3–6.6 秒，**6/6 复现不出 327 秒**。

另外查过两条排除路径：

- `compiler/prebake.py` **串行**预铸，无并发、无批量放大。
- `adapters/tts_omlx/transport.py` 请求体**不带 `ref_audio`**（无参考音频条件化），
  不是「参考条件化每次多花 ~5 秒」那条已知慢路。

所以**现有证据不足以指认根因**。此时任何「加时长重试」「加超时上限」
都是猜着改冻结区——那是本仓明令禁止的（先规格后代码 + 留口子优先于大重构）。
**本卡只负责把「猜」变成「不猜」。**

## 三、做什么

在 `labs/` 下建一个**可复现的端点可靠性探针**（`labs/omlx-reliability/`），
对着 `packs/heat_kefu/` 的**固定句集**跑，逐句记录：

- 请求墙钟耗时
- 返回音频时长
- 是否触发 quality 拒绝（> 30s 或静音超限）
- 失败时的完整错误文本

**固定语料 + 固定种子 + 固定轮次**（建议 3 轮 × 40 句 = 120 次请求，
按实测 1.4–8 s/句估算 5–20 分钟；跑不完就**如实报已跑数**，不许把部分结果写成全量）。

产物落 `labs/omlx-reliability/report.json` + 一份 `README.md` 写明口径
（样本量、轮次、句集来源、请求是否带参考音频、**统计口径 P50/P99/最大值**）。

## 四、验收

- AC1：`report.json` 里有 **最大值**与 **P99** 两个字段（只给均值会掩盖尾部——
  327 秒这种尾部事件在均值里看不见，这是本卡存在的理由）。
- AC2：探针**超时自杀**：单请求超过硬上限就打标记并继续，不许挂死整轮。
- AC3：跑批脚本**断言成功数 + 非零退出码**（跑批铁律：假绿比红更坏）。
- AC4：若**跑出了** 327 秒级样本 → 把触发句、请求体、响应头原样落盘，
  这就是 T66/T67 之外的第三个可复现根因入口。
- AC5：若**跑不出** → 报告如实写「N 次未复现，失败率 0/N」，
  **不许**写「已修复」或「无法复现即不存在」。

## 五、给维护者的判据（拿到 report.json 后）

| 观测 | 结论 | 下一步 |
|---|---|---|
| 出现 > 30 s 样本 | 服务端真会吐超长音频 | 单独开卡：时长预检（`labs` 侧先做，不动冻结区） |
| 全程正常、0/N 复现 | 当时的 3/4 失败**另有原因** | 查 Quick Start 当时的环境（并发？端点版本？PATH 里的 `ffmpeg`？） |
| 墙钟长但音频不长 | 网络/排队问题 | 与音频时长分开看，别混成一个指标 |

**在 AC5 结果出来之前，不要动 `quality.py` / `transport.py` 的时长逻辑。**

## 六、边界

- 探针**只读**外部端点，不写任何仓外/公司数据。
- 语料只取 `packs/heat_kefu/` 里**已在仓内**的话术，不引入新语料。
- 临时音频落 `/tmp`，跑完清干净，`git status -uall` 贴出来。

## 七、执行结果（2026-09-28，验收方回填）

`labs/omlx-reliability/` 已落：`probe.py`（零依赖、串行、超时自杀、成功数断言非零退出）
+ `README.md`（口径与取舍）+ `report.json`（120 条明细）。

| 指标 | min | P50 | P99 | **max** | mean |
|---|---|---|---|---|---|
| 请求墙钟 s | 1.1127 | 4.5503 | 12.8934 | **13.9941** | 5.0424 |
| 返回音频 ms | 1280 | 5200 | 13680 | **14480.0** | 6011.33 |

`counts`：`planned=120 executed=120 success=120 failed=0 timeout=0 quality_rejected=0`
`audio_over_30s=0`，`failure_rate=0/120`。

### 对 §五 判据表的结论：**走第 2 行**

**0/120 复现。** 端点在这个语料上表现稳定：最长音频 14.48 s，距 quality 的 30 s 阈值
有近 2 倍余量；**327 s 若真来自该句集，不是线性外推能触及的量级**。

→ 因此**不开**「时长预检 / 时长重试」卡。§一那次 3/4 Quick Start 失败**另有原因**，
应在当时的**环境**里查（本机 `PATH` 里的 `ffmpeg`、端点版本、是否并发），
而不是在 `quality.py` / `transport.py` 里猜着改。

### 顺带查出的三条事实（都写进 README 了）

1. **响应没有 `Content-Type` 也没有 `Content-Length`**（120 条全 `null`）——
   音频时长**无法从协议层预检**，只能解 WAV 头。
   这正是「要做时长预检就得先动冻结区」的根源，**是将来那张卡的成本所在**。
2. `transport` 默认 `timeout=600`（10 分钟）。**超时上限其实存在，只是不小**——
   「无超时」这个说法是错的，将来讨论超时不要重复这个误判。
3. 语料共 69 句，本次只取前 40；请求体**不带 `ref_audio`**（已由 `request_carries_ref_audio=false` 落证），
   排除「参考条件化慢」那条路径。

### 执行者的自我更正（已复核，结论采信）

跑批途中它自己发现并修了两个 bug：静音判据写成 `v <= 328` 而非 `|v| <= 328`
（16-bit 补码下把所有负样本当静音，一度误报 5 条 `head_silence_over`）、
AC3 断言语义写反。**它明确声明前两次跑批作废、本报告是修正版一次跑完的产物**，
并说「前两次跑出的『5 条全静音』是假的，不采纳」。

**这条自我作废的诚实度比报告数字本身更值得记**：跑批铁律说「假绿比红更坏」，
而「自己发现前两次结论是假的并作废」正是防假绿的那一步。
