## 12.1 一句话

> **前置包：把「流程已经决定要说的那些话」提前录成声音，按状态直接取。**
> **流程能定的，不经过模型；流程定不了的，才交给模型。**

## 12.2 它像什么、不是什么（**这一节是全部**）

### 12.2.1 三明治定位：夹在缓存与大模型中间（用户 2026-09-18 提法）

```
      快但没有逻辑            业务逻辑 + 规则化              慢但灵活
   ┌──────────────┐    ┌──────────────────────┐    ┌──────────────────┐
   │    缓存      │ <  │     前置包（我们）     │ <  │  大模型 / 端到端  │
   └──────────────┘    └──────────────────────┘    └──────────────────┘
    查表命中               按流程状态命中                每次前向推理
    但不知道自己在说什么     知道自己走到哪一步            什么都能说，但慢、不可审
```

| | 缓存（含语义缓存） | **前置包（我们）** | 大模型 / 端到端 |
|---|---|---|---|
| **响应** | 快 | **快**（磁盘读，实测 0.14 ms） | 慢（实测实时合成 515–587 ms 起） |
| **判断力** | 无 —— 只能命中"算过一模一样的" | **业务逻辑** —— 命中"走到流程的哪一步" | 强 —— 没见过的也能处理 |
| **灵活性** | 无 | **固定 / 规则化**——这是特性不是缺陷 | 灵活 |
| **可审核** | ⚠️ 存的是结果，看不出为什么 | ✅ **内容是数据，可 Review、可审批、可回归测试** | ❌ 行为在权重里，改不了也审不了 |
| **时效性 / 专业性** | 有 TTL 但内容黑盒 | ✅ **业务专业性由资产包供给；过期能被看出来并改** | ❌ 不知道你的业务细节，知识有截止点，过期只能重训 |

**用一句话说清三者的关系**：
**缓存快但不知道自己在说什么；大模型知道得多但慢且不可审；我们夹在中间——按流程知道该说什么，且说的每句话都能被人审核。**

**这也是"古法编程"的落点**：确定性的、显式的、规则化的逻辑。在 AI 时代，**显式规则反而成了稀缺品**——
因为它带来确定性、可审核、可回归测试（本项目八层 760 条测试、fail-closed、指纹校验，都是这个取向的产物）。

### 12.2.2 两处必须说准的精度（否则会吹过头）

1. **我们的"聪明"不是算出来的，是"提前知道"。**
   缓存也是"提前算过"，区别在于：缓存预先算的是**同一件事的答案**（必须先产生请求才知道查什么），
   我们预先知道的是**流程的下一步**（因为流程是我们设计的）。
   → **能力边界由此划定：流程没覆盖的判断，我们一概不如大模型，必须让位。**
   所以对外说"**比缓存聪明**"可以，说"**比大模型聪明**"不行。

2. **"时效性"上我们的真本事是"可修正"，不是"自动新鲜"。**
   我们同样会有过期话术。区别是：**过期能被看出来**（内容是显式数据，人一读就知道不对），
   改一行 JSON 重铸即可生效；而模型里的过期信息**只能靠重训**，且改之前没人看得出。
   → 所以时效性的正确说法是"**可审核、可修正**"。

### 12.2.3 像什么、不是什么

| 像什么 | 相同点 | **关键差别（别混）** |
|---|---|---|
| **IVR 预录音** | 都是提前录好、直接播 | 前置包按**流程状态**寻址（不是按键菜单），能插槽位、能走多轮、有未命中兜底与质检 |
| **音频缓存** | 命中就省掉合成 | 缓存按**内容**寻址：必须先算出来才知道能不能命中。**实测这条路命中率 0.00%**（LLM 措辞次次不同，99.4% 的句子全库唯一）。前置包按**状态**寻址，**命中是设计出来的，不是碰运气** |
| **微调 / 端到端模型** | 都能让固定的话不用现算 | 前置包是**数据不是权重**：改一句 = 改一行 JSON 重铸，可审核、可版本化、可回滚；命中是**磁盘读**（实测 0.14 ms），不是一次前向推理 |

**所以它不是"缓存语音"，是「按状态寻址的声音资产」。**
"缓存"这个词会把人带向"按内容寻址"，而那正是被实测否掉的那条路（`docs/11 §11.9.4`）。

## 12.3 它坐在哪

```
用户音频 → [ASR] → 文本 → [编排/状态机] → 「这一轮要说什么」 → [TTS] → 音频
                                              ↑
                                    前置包坐在这里（一个接缝）
```

**输入**：一个「要说什么」的表示（key + 槽位 + 语速档）。
**输出**：一段音频，以及它怎么播（语速/留白/开口策略）。
**不碰**：ASR、不猜"该说什么"、不做语义判定。
**慢路**（现场合成）永远保留作兜底；前置包只是让它大多数时候不被用到。

## 12.4 边界（实测钉住）

实测样本：1855 通真实客服电话 / 25810 个客服话轮。

| 话轮类型 | 由谁决定说什么 | 占比 | 前置包 |
|---|---|---|---|
| **流程性**：问候、确认身份、告别、合规提示、请稍等、未听清重试、转人工 | **流程** | **23.0%** | ✅ 命中率 100%（key 由流程给，实测 bench hit_rate = 1.0） |
| **内容性**：信息传达、提供建议、解决实施、共情 | **现场内容** | 77.0% | ❌ 每轮内容不同，句式 98%+ 不重复 |

**对外必须这么讲**：前置包让**流程决定的那部分**话术零延迟——**不是"全部固定部分"**。

## 12.5 这层还会产出一个东西：训练数据（微调弧线）

用户 2026-09-18 的洞察：*"小公司没钱训模型，只能用开源模型；开源模型的专业性又不合适，业务话术还得靠代码执行。
等规则收集够了，可以去训练一次，这样就有了自己的模型，可以对外输出、也可以开源。"*

**方向对，时机也对**——门槛已经从**算力**移到了**数据**：LoRA 微调 7B~9B 现在小公司付得起，
付不起的是**带标签的业务对话数据**。而前置包在运行中**顺带产数据**，且是人工审核过的高质量标注。

**但有一环必须接上**：前置包积累的配对（状态 → 话术）只覆盖**它自己覆盖的那 23%**，而那部分**规则本来就能做**；
真正需要模型的是 77% 的内容性话轮——前置包恰恰没有那部分数据。所以"攒够前置包数据 → 微调出替代大模型的模型"这条链断了一环。

修正后的弧线：

| 阶段 | 得到 | 得不到 |
|---|---|---|
| 开源模型 + 前置包（**现在**） | 固定话术零延迟、可审核、能上线 | 措辞不像本业务 |
| 攒够数据后 LoRA 微调 | **业务的措辞 / 语气 / 术语** | **业务事实**（今天的账务状态进不了权重） |
| 结果 | 模型负责那 77%，且说得像本业务 | **前置包仍要留着**：管固定的 23% + 事实注入 |

**所以不是"攒够数据就不再需要前置包"，而是"让模型更像你的业务，前置包继续管固定那部分"。**
每一段都能独立上线、独立产生价值——这正是小公司走得通的路。

**两条数据通道（这就是 §12.10 那两条留痕的用途）**：

| 通道 | 来源 | 用途 |
|---|---|---|
| **正样本**「该说什么」 | 轮级留痕（状态快照 + plan） | 监督微调数据 |
| **负样本**「哪里没覆盖」 | 事件流的 `miss` + `reason`（`key_not_prebaked` / `text_not_prebaked` / …） | **主动学习清单**：该补哪些 key、或该让模型接管哪些 |

**这两条现在加的成本几乎为零；事后补要改已冻结的事件契约。**

**最后一点：即使到了端到端模型，双工层仍然要外置。**
双工参数（耐心窗 / 打断 / 开口策略）在 E2E 模型里是权重里的东西——改不了、审不了、版本化不了。
所以哪怕模型训好了，这一层仍然需要一个外置的参数控制器。
这正是立项案论证"为什么这层是大厂缺口"的那一条，走通了微调弧线它依然成立。

## 12.6 包变大，命中率会上去吗（回答"猴子打字机"）

用户 2026-09-18 的提问：*"如果资产包够大够全、业务性够强，命中率是不是会越来越高？"*

**答案：分两个轴，一个涨、一个几乎不涨——而且两个轴对应的正是"经营路线"与"越来越大"两条路。**

| 轴 | 包变大意味着 | 命中率 | 为什么 |
|---|---|---|---|
| **key 轴（广度）** | 覆盖更多**流程步骤** | **不随包大小变化——设计对了就是 100%** | "该说哪句"由流程给出，与包多大无关。包大只影响**覆盖率**：业务里有多少比例的话轮被纳入了流程（§12.4 的 23% 会随覆盖变全而上升） |
| **variant 轴（深度）** | 同一个 key 有更多**说法** | 对 key 档**无用**；对自由文本档**收益次线性** | 自然语言变体空间是组合爆炸的，枚举式覆盖追不上 |

**为什么猴子打字机类比在这里失效**：猴子靠的是**无限时间**，而我们的预算是一轮对话的几十毫秒；
而且变体空间不是有限字母表——中文句子的可能组合是天文数字。**这不是"耐心够不够"，是"枚举能不能覆盖自然语言"，答案是不能。**

实测证据（`labs/corpus-harvest/raw/literal_baseline.json`）：2433 条真实话术 vs 34 条预铸 variant，
**最相近的 variant 相似度中位数只有 0.204**（P90 仅 0.360）——真实说法离我们的 variant 很远，
**不是"差一点就中"**。要让逐字命中从 0% 爬到门槛 98.7%，需要的 variant 数量是指数级的。

**结论：结构优先，规模其次。** 唯一能到 98.7% 的路是**把 key 空间闭合**（流程驱动），不是把变体堆多。

## 12.7 结构策略：先设骨架，再长内容

用户 2026-09-18 的问题：*"这些东西多了再展开再补充，还是提前设置好一个结构？"*

**答案：提前设骨架，内容自然生长。**

| 层 | 是什么 | 谁来定 | 能不能后加 |
|---|---|---|---|
| **骨架** | `script.json` 的流程 unit 序列——它**定义 key 空间** | **必须预先设计**（这就是"经营路线"） | ❌ 后改 = 改契约 |
| **内容** | 每个 key 的 `variants`（同一句话的不同说法） | 可以边用边补 | ✅ 加变体不动结构 |
| **垂直域** | 医疗、法律等独立业务 | **新增 `packs/<域>/` 目录** | ✅ 零内核改动（`packs/AGENTS.md:47`） |

- **医疗/法律这类"标杆业务"恰恰适合前置包**：它们知识密集但**流程相对固定**（问诊流程、法律咨询流程有标准步骤），key 空间是闭合的；
- **但它们是合规敏感域**：固定话术在医疗/法律场景可能构成"承诺"。这正好是项目"**可审核**"卖点的真实用武之地——
  前置包的内容是**数据、可 Review、可审批**，而模型权重里的行为审不了（R05 审批门）。

## 12.8 输出预算：1–200 字怎么变成可判据

用户 2026-09-18 的观察：*"人收取信息就在 1~200 字之间…超了 500~800 字就跟读作文，很累。"*

**这条对语音比文本更严——因为听不能跳读、不能回看。** 而"一条 variant = 一句"这条既有纪律
（`compiler/source.py:167-192`，句末标点 ≥2 即报错）**已经在防止单句过长**；缺口在**一轮播报的总量**
（一次 plan 可以把多个 unit 拼起来）。

**实测语速（fin-cs 包 102 条资产，去标点后计中文字符）**：

| 语速档 | 字/秒（中位） | 200 字要读 | 60 字要读 |
|---|---|---|---|
| slow | 3.76 | 53 秒 | 16 秒 |
| **normal** | **4.64** | **43 秒** | **13 秒** |
| fast | 6.57 | 30 秒 | 9 秒 |

**建议判据（做成 pack 级参数，缺省值可覆盖，但必须可判）**：

- **单轮播报 ≤ 60 字（≈13 秒 @normal）**——这是"一口气说清一件事"的上限；
- 超过则**必须拆轮**（plan 拆成多个 unit，轮间给用户插话机会），或改成一句**邀请**（"要不要我详细说？"）；
- 现有包最长句 27 字 ≈ 5.4 秒，说明**按"一句"纪律写的 assets 天然合规**，超预算只会发生在"拼接"这一步。

**落点**：`vox pack check` 对 plan 强制这条预算；超出 → 违规（不通过），而不是"警告一下"。
"不要写太复杂"这条要求因此从口感变成了**可判据**。

## 12.9 量大了会不会费劲（热路径的真实成本）

用户 2026-09-18 的提问：*"量很大了需要通过程序驱动、数据库驱动、Redis 驱动…调用起来是不是会费劲？"*

**先说当时的实话：热路径曾有真实的扩展性隐患**（`assets/pack.py:110-143`）——**2026-09-21 已由 T27 关掉**
（O(1) 索引 + 指纹预计算，10k 条下 0.5–0.8 µs；原状 102 条时无所谓）：

1. `lookup` 是**逐条线性遍历**（`for entry in self.assets`）——**没有索引**；
2. 每次命中**重算指纹**（sha256 over text+voice+rate+model）；
3. 每次命中做一次 **`audio_path.exists()`**（一次 stat 系统调用）。

102 条时无所谓；量大了这三样都要消掉。**正解不是换存储，是加载时建索引**：

| 现在 | 应该 |
|---|---|
| 线性遍历 | **加载时建 dict**：`(key, part_index, rate_key, variant) → entry`，热路径只查 dict |
| 每轮重算指纹 | 加载时校验一次（或 prebake 时已保证），热路径不重算 |
| 每轮 stat 文件 | 启动时一次扫描目录，之后不查盘 |

**Redis 的角色要说清（别提前上）**：
- **单机单进程：不需要**——内存 dict 比 Redis 快（没有网络往返）；
- Redis 真正的用途是 ① 多进程/多会话**共享一份索引**；② **TTL 失效通知**（见 T18）。
  **所以"上 Redis"的前提是"多进程"，不是"量大"。**
- **数据库不进热路径**：它是冷存储与审计用的。

## 12.10 留痕与存储：DB 还是日志（**现状是两者都没有**）

用户 2026-09-18 的问题：*"这个信息存的是存到数据库呢，还是程序跑落到日志上？"*

**先纠正前提**：写这一段时**两条都没有**（`Executor.execute()` 把事件放在内存里返回，
接缝层构造完就交出去，没有任何持久化）。**2026-09-19 起已补上**：轮级留痕由 **T17** 落地
（`trigger/` 的留痕通道，与既有事件流用 `turn_id`/`plan_id` 关联）。所以问题已从"要不要落"
变成"落下来的怎么用"——**T23 回流闭环**就是从这两条通道挖候选话术。

### 分三层，各按访问模式选

| 用途 | 存储 | 判据（为什么） |
|---|---|---|
| **热路径留痕**（每轮） | **JSONL 追加写**（本地，按天分文件） | 不阻塞播报、不依赖 DB 连接、断网也能跑。这才是"日志"的正当位置 |
| **训练数据快照**（离线导出） | **JSONL / parquet 快照**（仓外） | 训练脚本是**顺序扫**，不需要随机查——PG 在这件事上没有任何优势 |
| **查询 / 审核 / 统计** | **SQLite → PG** | 「哪些状态没有对应话术」「某 key 的未命中率」——**聚合与定位是 SQL 的强项**；人工审核的增删改查在这里 |

**写日志失败必须留痕**（本地缓冲 + 失败计数），不得静默丢——仓库红线。

### 别把训练数据塞进事件流

理由有二：① 事件流是**每轮每 unit 一条**的高频小记录，训练数据是**每轮一条**的低频大记录（状态快照可能几 KB），
混在一起会让日志膨胀、写入变慢；② **事件契约在冻结区**（`core/metrics_spec.py`），
为了塞训练字段而反复改冻结契约，成本远高于收益。

**正解：分成两条通道，用 `turn_id` / `plan_id` 关联——而这两个字段事件流里已经有了**
（既有设计的红利，一个新字段都不用加）：

| 通道 | 内容 | 频率 |
|---|---|---|
| **事件流**（照旧，不改契约） | 我播了什么、命中没命中、为什么 | 每 unit 一条 |
| **轮级留痕**（新增，T17 的产物） | **当时的状态快照 + 产出的 plan** | 每轮一条 |

两者用 `turn_id` / `plan_id` 拼起来，就是训练样本。

### 给 Java 背景的一个转弯：增删改查的对象不是数据库行

**对的地方**：查 / 审 / 改确实该有 DB——你要的"快速定位、赶紧改"，靠 SQL 聚合最快。

**要转弯的地方**：前置包的"改话术"**不是 UPDATE 一行数据库，而是「改 JSON 源码 → `vox pack check` → 重铸」**。

- `packs/<业务>/phrases.json` 是**源码**，manifest + 音频是**编译产物**；
- 改话术 = 改源码 + 重新编译 → **天然带 diff / 版本 / 回滚 / 灰度**
  （`packs/AGENTS.md §六` 定的 Git 式流程：话术 diff → check → build → bench → 灰度 → 放量）；
- 一旦改成"UPDATE 数据库一行"，你会**当场丢掉 diff / 回滚 / 灰度**——而这三样正是本项目"**可审核**"卖点的全部；
- **所以：源码是真相源（Git 管），DB 管轨迹与统计。别让 DB 成为话术的真相源。**

### 一条现在就要划的红线：配对里什么能存

`(状态快照, 话术)` 配对里，**"话术"是我们自己写的（不敏感），"状态快照"可能含用户信息**（账号、金额、工单）。

所以 T16 定 `state` 格式时**必须同时分层**：

| 层 | 例子 | 能去哪 |
|---|---|---|
| **结构化字段** | 状态码、key、枚举值、布尔 | 可入库、可导出、可进公开 demo |
| **敏感值** | 账号、金额、原始文本 | **只落本地**，不入公开仓，导出时脱敏或替换为占位 |

这与既有敏感数据红线一致，而**现在划分的成本几乎为零，事后补要改已冻结的契约**。

**判据强度的诚实说明（2026-09-19 T17 实现暴露后补）**：T16 的实现按**字段名标记**兜底判定哪个字段敏感
（`account` / `phone` / `amount` / `balance` / `name` / `text` / `secret` / `token` 等 16 个标记），
**不解析值**。因此它是**一道 lint，不是保证**：一个名叫 `order_ref`、装着客户标识的字段，
被声明成 `structured` 也不会报错。

**所以真正的保证来自三层叠加，不要只指望嗅探**：
1. 包作者**显式**声明每个字段的层（未声明字段一律报错，不会默认放行）；
2. 名字嗅探拦截常见误声明（声明为 structured 但名字命中标记 → 报错）；
3. **人工 Review `trigger.json` 的 `state_fields`** —— 这正是本项目「可审核」支柱的落点。

**候选改进（未做，需权衡误报）**：把名字嗅探从「denylist 拦截」改成「allowlist 放行」
（未显式声明为 `structured` 的字段一律当敏感），或对值做模式识别。前者更强但会挡住合法用法，
后者会产生误报——两者都要业务侧参与定，因此**登记为候选而非现在改**。

## 12.15 宿主无关性与引用纪律（**用户拍板 2026-09-23**）

> 这一节回答「前置包和外面的框架是什么关系」。**它是定位的一部分，不是实现细节。**

### 12.15.1 一条原则

**vox-type 是前置包，不依附任何框架。**

- 它对外提供的是**能力**（按状态取已预铸的音频），不是**某个框架的插件**；
- 「接进某个框架」这件事永远是**我们写一个适配器去适配它**，
  **不是我们改自己以迁就它**，更不是把它的抽象变成我们的内核。

### 12.15.2 引入第三方，三步走（缺一步都不算引入）

| 步 | 做什么 | 反例（不允许） |
|---|---|---|
| ① **变成我们体系里的一个部件** | 落 `adapters/framework_<宿主>/`，遵守 `adapters/AGENTS.md` 的七项纪律与 ≤150 行可执行行预算 | 把对方的类直接 import 进 `runtime/`/`core/` |
| ② **说清引用关系** | 适配器 docstring + 卡的验收记录里写明：依赖对方哪个**公开抽象**、基线 commit/版本、破损时怎么发现 | 只写"基于 X 项目" |
| ③ **留口子** | 只走对方公开面（不 import 私有名）；对方版本变动导致的破损要**响亮留痕**（同 `framework_kefu` 的处置） | 静默降级回落到原路而不计数 |

**单向依赖**：我们依赖它的公开接口，**它不依赖我们**。所以永远是「我们的适配器适配它」。

### 12.15.3 这条原则的三条推论

1. **前端（适配器）可以换，中段（前置包）不动**：换宿主 = 新写一个 `adapters/framework_*`，
   `compiler/ assets/ runtime/` 一行不改（D9 冻结区的价值正在这里）。
2. **「任意 Agent 需要语音时都能从这里取」——靠的是能力接口，不是框架绑定**：
   对外的最小面是「给一段文本（或一个 key + 槽位），还一段 16k 音频 + 一条事件」。
   任何宿主只要能把「这一轮要说什么」表示出来，就能挂上（`docs/21 §3.1` 的 Pipecat 即实例）。
3. **不许出现「为了接 A 框架而改内核」**：真出现说明抽象选错了，
   应当在 `adapters/` 里加一层转换，而不是让内核长出 A 的形状。

### 12.15.4 已核查的宿主与接缝（2026-09-23）

本节只记结论：**Pipecat 是最强接缝（官方抽象方法 `TTSService.run_tts` + 已有 `CachingTTSService` 先例）**；
